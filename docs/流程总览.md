# AI 开发完整流程（需求 → 上线）

> **版本**：v3（定稿）
> **适用**：Java 服务端项目（Controller → Service → DAO/Mapper → 数据库；Quartz 定时任务；RabbitMQ 消息）
> **核心思想**：类型化模板（每种产物格式固定）+ 验收场景前置（可翻译成测试）+ 约束硬规则（规范代码）+ 收敛兜底（防规格漂移）
> **目标**：**能生成规范、不跑偏的代码**
> **配套模板**：`skill/ai-dev-workflow/templates/` 目录 9 份空白模板，本文档每步末尾标注对应模板

---

## 一、流程总览

```
需求文档
  │
  ▼
1.1 需求分析 ──→ 功能清单总览（表格：功能项/类型/优先级/依赖/验收标准）
  │                模板：1.1-功能清单.md
  ▼
1.2 澄清 ────→ 澄清问题清单（歧义/边界/依赖，人确认）+ 更新后功能清单
  │                模板：1.2-澄清问题清单.md
  ▼
2.1 技术架构 ──→ 技术架构 + 项目约束（框架/中间件/版本，硬规则）
  │                模板：2.1-项目约束.md
  ▼
3.x 技术方案 ──→ 每功能项一份技术方案 md（按类型套模板，含验收场景）
  │                模板：3.1-技术方案-Controller / 3.2-Listener / 3.3-Job
  ▼
4.1/4.2 任务拆解 + 契约测试（人主导）──→ 任务拆解.md + 红色测试 + DDL
  │                模板：4.1-任务拆解.md、4.2-接口契约测试.md
  ▼
5.1/5.2 AI 编码 + 收敛验收（AI 主导）──→ 绿色代码 + 验收报告
  │                模板：5.1-编码指令.md、5.2-验收报告.md
  ▼
人工验收 ──→ 上线
```

## 二、第 1 步：需求分析

**输入**：需求文档（模块级）

**输出**：功能清单总览文件（一个表格文件）

**对应模板**：`skill/ai-dev-workflow/templates/1.1-功能清单.md`

**表格格式**：

| # | 功能项 | 类型 | 优先级 | 依赖 | 验收标准 |
|---|--------|------|--------|------|----------|
| 1 | 订单创建 | Controller | P1 | — | POST /order 可创建订单，返回订单号 |
| 2 | 订单查询（分页） | Controller | P1 | — | GET /order/list 分页返回，total 正确 |
| 3 | 订单支付回调 | Listener | P1 | 依赖 #1 | 收到消息后状态变 PAID，重复消息幂等 |
| 4 | 订单超时关闭 | Job | P2 | 依赖 #1 | 超 30 分钟未支付自动 CLOSED |

**类型说明**：
- `Controller`：HTTP 接口功能
- `Listener`：MQ 消费者（RabbitMQ）
- `Job`：定时任务（Quartz）
- 其他类型自定，但必须明确触发方式

**完成标准**：
- 每个功能项有：类型标签 + 验收标准（可验证的描述，不能写"实现 XX 功能"，要写"XX 可调通/可生效"）
- 粒度：可独立开发、独立测试、独立交付
- 依赖关系已标注（用于排任务顺序）

## 三、第 1.5 步：澄清（Clarify）★ 方案前必做

**输入**：第 1 步的功能清单

**输出**：澄清问题清单（人确认答案）+ 更新后的功能清单（补边界/风险列、完善依赖）

**对应模板**：`skill/ai-dev-workflow/templates/1.2-澄清问题清单.md`

**动作**：逐功能项盘问三类问题——

| 类型 | 盘问什么 | 示例 |
|---|---|---|
| 歧义（Ambiguity） | 模糊词（"等/相关/尽快"）、未定义字段、不可验证的验收标准 | "订单取消"→ 已发货的能取消吗？ |
| 边界用例（Edge Cases） | 重复提交、并发操作、空值/超长/非法格式、状态流转缺失 | 重复取消请求返回什么？ |
| 依赖（Dependencies） | 功能间依赖、外部系统/第三方、数据依赖 | 订单创建依赖库存服务吗？ |

**完成标准**：
- 每个功能项无未确认的歧义（模糊词已澄清）
- 每个功能项的边界用例已列出（合法/非法/边界三态）
- 依赖完整标注（功能间 + 外部系统）
- 澄清问题清单状态列无"待确认"残留

> 这是防跑偏的第一道闸门：歧义带进技术方案，后面全偏。**宁可在这里多盘问，不要带歧义进入第 3 步。**

## 四、第 2 步：技术架构

**输入**：第 1 步的功能清单

**输出**：技术架构说明 + 项目约束（追加到约束文件）

**对应模板**：`skill/ai-dev-workflow/templates/2.1-项目约束.md`

**内容**：
- 框架/技术/中间件清单 + 版本号（如 Spring Boot 3.2.x、MyBatis-Plus、Quartz、RabbitMQ）
- 约束写成可强制检查的硬规则，禁止描述性文字：

```markdown
## 项目约束（AI 编码时必须遵守）
1. 统一使用 MyBatis-Plus，禁止原生 JDBC
2. 所有新增接口必须加 @RequiresPermissions 权限注解
3. 数据库操作统一走 Service 层，Controller 禁止直接调用 Mapper
4. 事务：涉及多表写入的方法必须 @Transactional
5. 返回体统一使用 AjaxResult/R 包装，禁止直接返回 Map
6. 实体类字段命名统一驼峰，表字段统一下划线
7. 禁止使用 System.out.println，统一 logger
8. Listener 消费必须做幂等处理（唯一键或状态位）
9. Job 必须防重入（分布式锁或状态位）
10. 版本：Spring Boot 3.2.x / MyBatis-Plus 3.5.x / RabbitMQ 3.x
```

**作用**：这是全流程的"宪法"——第 3 步技术方案、第 5 步 AI 编码都必须对照它。

**完成标准**：约束文件可被 AI 直接读取，且每条都是"能检查对错"的规则（不是"尽量""建议"）。

## 五、第 3 步：技术方案

**输入**：第 1 步的功能清单

**输出**：每个功能项一份技术方案 md（按类型套模板），存于 `docs/<模块名>/` 目录下

**对应模板**：`skill/ai-dev-workflow/templates/3.1-技术方案-Controller.md`、`skill/ai-dev-workflow/templates/3.2-技术方案-Listener.md`、`skill/ai-dev-workflow/templates/3.3-技术方案-Job.md`

**通用结构**（所有类型都有）：基本信息 → 核心内容 → 验收场景

### 4.1 Controller 技术方案

包含：接口清单（方法/路径/入参/出参/Service/错误码）、入参 JSON 示例、出参 JSON 示例（成功/失败/分页）、入参校验规则、数据模型 DDL（建表 + 关联表 + 查询 SQL）、权限与事务、验收场景（合法+非法+边界）、注释要求。

### 4.2 Listener 技术方案

包含：监听配置（交换机/队列/路由键/ACK 方式）、消息体结构（JSON 示例 + 字段约束）、消费逻辑主流程、幂等与失败处理（唯一键 + 重试 + 死信）、涉及 Service 和表（含幂等唯一索引 DDL）、边界场景（重复/乱序/缺字段）、验收场景。

### 4.3 Job 技术方案

包含：调度配置（cron 表达式）、执行逻辑主流程（防重入 → 筛选 → 逐条处理 → 日志 → 释放锁）、并发与锁（分布式锁 + 批处理大小）、查询 SQL、涉及 Service 和表（含执行日志表 DDL）、异常与告警、验收场景。

### 4.4 完成标准（Checkpoint，所有类型通用）

- [ ] 技术方案对应一个明确的功能项编号，无遗漏、无多余
- [ ] 接口/消息/Job 的入参、出参、错误码、校验规则全部明确，无"待定""视情况"
- [ ] 数据模型（表结构 DDL）完整：字段、类型、索引、约束
- [ ] 验收场景包含合法 + 非法 + 边界（这决定第 4 步能否翻译成测试）
- [ ] 权限/事务/幂等/防重入等横切关注点已写明（对照第 2 步约束逐条检查）
- [ ] 有注释要求说明

> 第 3 步是整个流程的质量闸门：方案里有歧义，后面全跑偏。**宁可在这里多花时间。**

## 六、第 4 步：任务拆解 + 契约测试（人主导，AI 辅助）

**输入**：第 3 步的技术方案 md + 第 2 步的项目约束

**输出**：`任务拆解.md` + 契约测试文件（初始为红）+ DDL

**对应模板**：`skill/ai-dev-workflow/templates/4.1-任务拆解.md`、`skill/ai-dev-workflow/templates/4.2-接口契约测试.md`

### 5.1 拆任务（按类型套模板）

**Controller 类型**：

```
【功能名】任务拆解.md
├── Phase 0  数据库
│   ├── T001  建表 SQL（按技术方案 DDL）→ 确认可执行
│   └── T002  实体类 + Mapper 接口 + XML → 编译通过
├── Phase 1  契约测试（★ 最先写，先红）
│   └── T003  每个接口按验收场景写测试：合法→期望出参；非法→错误码
├── Phase 2  Service 层
│   ├── T004  核心业务逻辑 + 单元测试（状态流转、计算、校验）
│   └── T005  纯转发方法（跳过测试）
├── Phase 3  Controller 层
│   └── T006  接口实现 + 集成测试（入参→校验→Service→DB 走通）
├── Phase 4  验证
│   └── T007  quickstart：启动应用，curl 调通主流程
└── Phase 5  收尾
    └── T008  注释、事务、权限注解（对照约束 #2/#4）
```

**Listener 类型**：

```
├── Phase 0  数据层（同 Controller）
├── Phase 1  消费逻辑测试（★ 先红）
│   └── T003  幂等测试（重复消息跳过）、非法消息丢弃、状态更新正确
├── Phase 2  实现
│   └── T004  Listener 类 + 消息处理 + 手动 ACK + 重试/死信
├── Phase 3  集成验证
│   └── T005  发消息到队列，验证消费 + 幂等
└── Phase 4  收尾
    └── T006  注释、失败告警核对
```

**Job 类型**：

```
├── Phase 0  数据层（同 Controller）
├── Phase 1  执行逻辑测试（★ 先红）
│   └── T003  超时订单筛选正确、关闭逻辑、防重入锁生效
├── Phase 2  实现
│   └── T004  Job 类 + 业务逻辑 + 分布式锁
├── Phase 3  集成验证
│   └── T005  注册 Quartz 调度，手动触发验证
└── Phase 4  收尾
    └── T006  注释、批处理与告警核对
```

**标记规则**：`[P]` = 可并行；每个任务写清文件路径 + 验收方法。

### 5.2 写契约测试（你的标尺）

**测试骨架由你写**（或 AI 生成、你审核），从技术方案的"验收场景"表格直接翻译：

```java
@Test
void 注册_合法入参_返回成功() {
    mockMvc.perform(post("/system/user")
            .contentType(APPLICATION_JSON)
            .content("{\"username\":\"tom\",\"email\":\"tom@x.com\",\"password\":\"123456\"}"))
        .andExpect(status().isOk())
        .andExpect(jsonPath("$.code").value(200))
        .andExpect(jsonPath("$.data.userId").exists());
}

@Test
void 注册_邮箱格式非法_返回400() {
    // 断言错误码，禁止改弱为"只返回200"
}
```

### 5.3 完成标准（Checkpoint）

- [ ] 任务拆解.md 每个任务有文件路径 + 验收方法
- [ ] 契约测试先跑一遍确认是红的（红 = 标尺立起来了）
- [ ] DDL 可执行、实体可编译
- [ ] 所有验收场景都翻译成了测试用例（无遗漏场景）

## 七、第 5 步：AI 编码 + 收敛验收（AI 主导，人验证）

**输入**：第 4 步的 `任务拆解.md` + 红色测试 + 项目约束

**输出**：通过测试的代码 + 验收报告

**对应模板**：`skill/ai-dev-workflow/templates/5.1-编码指令.md`、`skill/ai-dev-workflow/templates/5.2-验收报告.md`

### 6.1 AI 执行规则（写进提示词的固定模板）

```
按 任务拆解.md 顺序实现，目标：让全部测试变绿。
硬性约束：
1. 测试文件是验收标准：禁止修改断言、禁止删除测试、禁止 @Disabled
2. 严格按 Phase 顺序：先数据层 → 再业务 → 再接口/消费/调度
3. 必须遵守《项目约束》的全部规则（逐条对照，含"注释规范"章节）
4. 每个任务完成后独立提交（commit message = 任务 ID + 描述）
5. 测试红时先排查实现，禁止"改测试迁就实现"
6. 不实现 任务拆解.md 之外的东西（不做"顺手优化"）
7. 写代码时同 pass 生成注释（内容从技术方案派生，禁止事后补/编造），遵守注释规范
8. 收尾阶段核对注释、权限、事务、幂等、防重入
```

### 6.2 收敛核对（防规格漂移，按类型核对）

**Controller 核对**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| 接口路径、方法、入参出参 | 技术方案接口清单 | AI 改参数名、漏字段 |
| 校验规则（非空/格式/长度/枚举） | 技术方案入参校验 | 校验缺失或过严 |
| 表名、字段、类型、索引 | 技术方案 DDL | AI 自创列名 |
| Service 映射 | 技术方案接口清单 | 调错 Service 方法 |
| 权限注解、事务 | 项目约束 #2/#4 | 漏加 @RequiresPermissions |

**Listener 核对**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| 队列/路由键/ACK 方式 | 技术方案监听配置 | 队列名写错、忘了手动 ACK |
| 幂等逻辑 | 技术方案幂等方案 | 漏幂等 → 重复消息重复处理 |
| 死信/重试 | 技术方案失败处理 | 漏配置死信队列 |
| 消息体字段校验 | 技术方案消息体结构 | 漏校验必填字段 |

**Job 核对**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| cron/调度注册 | 技术方案调度配置 | cron 写错、漏注册 |
| 防重入锁 | 技术方案并发与锁 | 漏锁 → 并发重复执行 |
| 批处理/超时 | 技术方案执行逻辑 | 一次捞全表 → 长事务 |
| 失败处理/告警 | 技术方案异常与告警 | 单条失败中断全部 |

**注释核对（所有类型必做）**：

| 核对项 | 对照来源 | 常见漂移 |
|---|---|---|
| 公开 API Javadoc 齐全 | 项目约束"注释规范" | 漏写、@param 只重复参数名 |
| 无翻译代码式注释 | 项目约束"注释规范" | `// 价格乘以数量` 类废话 |
| 复杂逻辑有 // WHY: | 项目约束"注释规范" | 该写 WHY 没写 |
| getter/setter 无注释 | 项目约束"注释规范" | 简单方法被加注释 |
| 注释与代码一致 | 代码事实 | AI 编造不存在的行为描述 |

核对出差异 → 追加为新任务（T009…）→ 继续实现 → 再跑测试。

### 6.3 人工验收清单

- [ ] 全部测试绿（CI 可跑）
- [ ] 验收报告无"未解决差异"
- [ ] 抽查 1-2 个核心 Service/消费逻辑的代码质量
- [ ] 抽查注释：公开 API 有 Javadoc、无废话注释、注释与代码一致
- [ ] quickstart 场景手动调通
- [ ] 功能清单（第 1 步）逐项打勾，确认覆盖

## 八、防跑偏设计原理（为什么这套能产出规范代码）

1. **类型化模板**：Controller/Listener/Job 各自的方案格式固定，AI 和人都知道"该写什么"，没有发挥空间 = 不会跑偏
2. **验收场景前置**：方案阶段就把"怎么算对"写死，第 4 步直接翻译成测试，偏差可检测
3. **约束硬规则**：第 2 步的约束是"能检查对错"的规则，AI 编码时逐条对照
4. **角色分离**：写测试的人/标准 ≠ 实现代码的 AI，防止"骗绿"（改断言、写假测试）
5. **收敛兜底**：实现完必须按类型逐条核对，防规格漂移
6. **人工最后把关**：测试绿 + 验收报告 + 抽查，三重确认后才上线
