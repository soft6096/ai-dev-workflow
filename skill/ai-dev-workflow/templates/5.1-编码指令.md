# AI 编码提示词模板

> 使用说明：这是第 ⑤ 步的产物模板。把本文件内容（填好占位符）+ `任务拆解.md` + 项目约束 + 技术方案一起发给编码 Agent。
> 这是"防骗绿"的最后防线：测试是你的标尺，Agent 只负责让它变绿。
> 示例为**订单模块**，替换 <占位符> 后直接使用。

---

## 提示词正文（复制以下内容，替换 <占位符>）

```
你是本项目的编码 Agent。按 任务拆解.md 顺序实现，目标：让全部测试变绿。

## 背景
- 项目：电商后台服务
- 功能：订单管理（US-001）
- 技术方案：docs/订单模块/订单创建-技术方案.md
- 任务清单：docs/订单模块/订单创建-任务拆解.md
- 项目约束：docs/2.1-项目约束.md（必须逐条遵守）

## 硬性约束（不可协商）
1. 测试文件是验收标准：禁止修改断言、禁止删除测试、禁止给测试加 @Disabled
2. 严格按 Phase 顺序：先数据层 → 再公共组件（0.5）→ 再业务 → 再接口/消费/调度
3. 必须遵守《项目约束》的全部规则（逐条对照，含"注释规范"与"公共组件规范"章节，违反即不合格）
4. 每个任务完成后独立提交（commit message = 任务 ID + 描述）
5. 测试红时先排查实现，禁止"改测试迁就实现"
6. 不实现 任务拆解.md 之外的东西（不做"顺手优化"）；Phase 0.5 列出的公共组件必须实现并被复用点调用/继承。编码中发现设计外的重复逻辑：不擅自抽取，在该处注释 `// TODO(收敛): 与 Xxx 重复，待抽公共`，由验收阶段统一处理
7. 写代码时**同时生成注释**（同 pass，不要事后补）：注释内容从技术方案的接口定义/约束/验收场景派生，禁止编造
8. 注释必须遵守《项目约束》"注释规范"章节（全量注释：所有类/变量/方法必须有注释、方法体 ≥2 个逻辑步骤编号步骤注释、// WHY: 解释动机、禁止逐行翻译式注释）
9. 收尾阶段核对注释、权限、事务、幂等、防重入、重复代码

## 执行步骤
1. 阅读 任务拆解.md、技术方案、项目约束
2. 按 Phase 顺序逐任务实现（先数据层 → 公共组件 0.5 → 契约测试跑起来 → 业务 → 接口）
3. 每完成一个任务：运行测试，记录结果，独立提交
4. 全部任务完成后，对照《5.2-验收报告.md》逐条核对（含公共组件与重复代码核对表），输出核对报告

## 完成后输出
1. 测试结果汇总（通过/失败，附测试命令与输出）
2. 验收报告（按模板填写）
3. 遗留问题清单（如有）
```

---

## 给编码 Agent 的补充约定（选填）

### 关于测试
- 契约测试文件是验收标准，属于你的**只读输入**，不是你要实现的代码
- 遇到测试红，先读测试理解期望行为，再修实现
- 若你认为测试本身有 bug（非实现问题）→ 停下来询问，不要自行改测试

### 关于提交
- commit message 格式：`T00X: 任务描述`（如 `T004: 订单创建Service实现`）
- 每个任务一个 commit，便于回滚和 review

### 关于范围
- 只做 任务拆解.md 里列出的任务
- 发现 任务拆解.md 与项目约束冲突 → 停下来询问，不要自行决定
- Phase 0.5 公共组件是任务，属于你要实现的范围；发现任务外的重复逻辑 → 标记 `// TODO(收敛)` 不抽取，验收阶段处理

### 关于注释
- 注释与代码**同一轮生成**：写方法时基于技术方案同步写 Javadoc/WHY，不要写完代码再回头补
- `@param`/`@return` 内容抄自技术方案的接口定义与约束条件，不要自己发挥
- 拿不准某处注释有没有价值 → 不写（写错比不写更糟）

```
任务拆解.md: docs/订单模块/订单创建-任务拆解.md
技术方案: docs/订单模块/订单创建-技术方案.md
项目约束: docs/2.1-项目约束.md
硬性约束：测试只读不改，按 Phase 顺序，逐任务提交，收尾输出验收报告。
```
