# 功能清单（需求分析）

根据输入的需求文档/需求描述，生成**功能清单总览文件**。**这一步决定需求是否被完整实现**——拆漏一个需求点，后续方案/编码/验收全链缺失。

## 输入

- 需求文档（模块级）或用户直接给出的需求描述

## 执行

0. **过滤非 Java 服务端需求**（本流程只开发 Java 服务端需求）：
   - 从需求文档中识别**非 Java 服务端需求**：前端页面/移动端 App/小程序/其他语言服务端/纯运维配置等
   - 这些需求**不拆功能项、不进入本流程开发范围**，记入"非 Java 服务端需求（已过滤）"清单（见模板 1.1 对应章节），标注：需求点、原因（如"前端页面，非 Java 服务端"）、建议承接方（**前端需求可走 vue-ai-dev 流程**，如已安装）
   - 只对 Java 服务端需求（Controller/Listener/Job/无入口）拆功能项

1. **列需求点清单**（需求追溯的前提）：把需求文档逐条拆成**需求点**（每条一行：编号 + 需求描述 + 来源段落），先不急着拆功能项——**先穷尽需求，再设计功能**。需求点粒度 = 一条可独立判定"做没做"的需求表述（如"用户可修改密码"）。

2. **存量适配（可选）**：若本模块开发已走 0.5 存量扫描，拆功能项前**对照 `docs/0.5-存量代码扫描.md`**——老项目已有功能/表结构/可复用组件，避免重复建设或与老功能冲突（新需求若与老功能重叠，先标记出来交 1.2 澄清确认是否复用/改造）。

3. **拆功能项**（每项一行，填入表格；**粒度标准 + 正反例见模板**）：

   | # | 功能项 | 承接需求点 | 类型 | 优先级 | 依赖 | 验收标准 |
   |---|--------|-----------|------|--------|------|----------|
   | 1 |  | #R1 | Controller/Listener/Job | P1/P2/P3 | 依赖 #编号 或 — | 可验证的描述 |

   - **粒度规则**：一个功能项 = 一个**可独立验收的用户可感知能力**——一个 HTTP 端点 / 一个 MQ 消费逻辑 / 一个 Job / 一组内聚的 CRUD（同实体多端点合并一项）
   - **模糊需求处理**：拆项时遇到无法拆解的模糊需求（没说清入口/行为）→ 该功能项状态标**"待澄清"**，不强行拆解（歧义留给 1.2 澄清优先处理），在功能清单"拆解说明"标注"待澄清：XX 点"

4. 类型说明：
   - `Controller`：HTTP 接口功能
   - `Listener`：MQ 消费者（RabbitMQ）
   - `Job`：定时任务（Quartz）
   - 其他类型须注明触发方式

5. **验收标准必须可翻译成契约测试断言**（弱 → 强示例见模板）：
   - 弱（不合格）："实现订单创建" / "订单创建可调通"
   - 强（合格）："POST /order 传入合法参数 → 返回订单号，订单落库状态 PENDING；传入非法参数 → 400 错误码 + 字段校验提示"
   - 每条验收标准 = **输入 → 预期输出/状态变化**，能直接翻译成 4.2 测试用例

6. **需求覆盖核对（防遗漏，必做）**：拆完功能项后，**逐条对照需求点清单**：
   - 每个需求点必须至少被一个功能项"承接"（功能项表格"承接需求点"列）
   - 没有承接的需求点 → 要么补功能项，要么明确标记"已过滤（记原因）/ 延后（记版本）"——**不允许静默消失**
   - 核对结果写入模板"需求覆盖核对"章节（表格：需求点 → 承接功能项 / 已过滤 / 延后）

7. **MVP 版本切分**：P1 集合 = **本期最小可交付**（MVP）；P2/P3 标后续版本。模块信息"本期范围"写明"本期交付：P1（可选 + P2 部分）"，需求文档范围超本期时在拆解说明标注"延后项"。

8. **记录非功能需求**：需求文档中的性能/安全/审计/日志等非功能需求 → 记入模板"非功能需求"章节（标注落地位置：2.1 约束 / 3.x 方案），不混入功能项表格。

9. **读取版本号并创建版本化目录**：从需求文档/PRD 中读取模块**版本号**（V 开头，如 V1.2.0；需求文档未标注版本号则向用户询问），生成目录名 `<模块名>V<版本号>-<YYYYMMDDHHMMSS>`（时间戳 = 生成时刻），并在该目录下创建 `1.1-功能清单.md`。后续所有产物（1.2/2.1/3.x/4.1/5.2）都落入该目录，目录名一旦创建不再变更。

## 输出

`docs/<模块名>V<版本号>-<YYYYMMDDHHMMSS>/1.1-功能清单.md`（参考模板 `templates/1.1-功能清单.md`，文件名带 1.1 编号，与流程步骤对应）

## 完成标准

- [ ] 非 Java 服务端需求已过滤并记录（模板"已过滤"清单非空时：每项有原因 + 建议承接方）
- [ ] **需求点清单已穷尽**（需求文档逐条拆解，无遗漏段落）
- [ ] **需求覆盖核对通过**：每个需求点有承接（功能项 / 已过滤 / 延后），无静默消失
- [ ] 每个功能项有类型标签 + **可翻译成测试断言的验收标准** + 依赖标注 + 承接需求点
- [ ] 粒度符合标准（可独立验收；无拆太细/太粗，正反例见模板）
- [ ] 模糊需求已标"待澄清"（未强行拆解）
- [ ] MVP 切分明确（本期交付范围 = P1 集合）
- [ ] 非功能需求已记录（性能/安全/审计，标注落地位置）
- [ ] 通过 `/clarify` 完成歧义/边界/依赖澄清后，才可进入技术方案（`/design-*`）
